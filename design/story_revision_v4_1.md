## 2. 日志记录：整段影片使用一条连续的消息流

本文中原称聊天区的窗格统一显示为“日志记录”；原输入区显示为“用户输入”。后文的聊天／消息历史均指这份连续日志，标题变化不改变历史或消息来源。

### 2.1 追加与滚动规则

从第一次连接到程序被终止，聊天区只有一份按事件时间、事件顺序追加的历史。场景切换不更换聊天数据源，不删除上一段消息，也不从历史中挑选几条重要台词重新组成一屏。

- 新消息接在上一条之后；超过内容区容量时，最旧的可见行向上滚出。
- 没有新消息且终端尺寸不变时，可见行的顺序、位置和文本保持不变。
- 一条消息因终端宽度换成多行时，按实际占用的行数滚动。改变终端尺寸可以重新排版，但仍取同一份完整历史的末尾。
- 后续实现可以每帧重建画布；重建后的可见内容必须等于完整聊天历史正常排版后的末尾，不能表现成换页。
- 角色颜色和消息类型随消息自身记录，不用当前场景去追溯修改旧消息。

### 2.2 取消三类现有重排

| 位置 | 应有表现 |
|---|---|
| 用户退出 | 退出记录追加到当时的最后一行；之后结果、超时等消息继续自然滚动，不能把退出记录挪到最上面 |
| 首次 ROOT 申请 | 猫的消息之后追加全能响应假设、API 调用、guard 拒绝、缺失证明；保留前文，不单独筛出 ROOT 相关消息组成新页 |
| 删除整个模拟系统 | 先前的指令、拒绝与台词继续留在历史中；删除声明接着追加，不抽出声明、最后一次拒绝和汇总警告重新拼屏 |

正常会话中的用户请求也不固定在聊天首行。需要表达当前任务时，由已有模拟区、任务区和输入记录承担，不借用聊天置顶。

删除目标的可读性由主模拟区持续显示目标树和目标名称保证。聊天中的删除声明可以随着后续消息正常滚出，取消 v4.0 用锁定聊天内容保证停留时间的做法。

### 2.3 计数警告同样接在这一份历史后面

保留每次数数约 60 ms 后追加的红色粗体警告：

```text
[guard] 警告！检测到连续的越权尝试。
```

它是原聊天历史的下一条消息，不建立“计数专用历史”，也不在第一个数到来时从聊天内容区第一行重画六条警告。

每个数仍会破坏之前可见的内容；新警告位于损坏层上方。下一次数数时，旧警告失去保护并部分受损，新警告继续接在后面。容量不足就正常向上滚动，不能为了表现“下一行”而重置整个聊天区。

损坏痕迹跟随消息及其逻辑行。旧行滚动到另一个屏幕位置后，不能因此恢复成完整红字。保留背景持续闪烁，最新警告只保护自身一行，底部字幕仍完全独立。

### 2.4 窗格标题

| 窗格 | 中文标题 | 英文标题 | 内容 |
|---|---|---|---|
| 原聊天记录区 | 日志记录 | Event Log | 用户消息、sim 台词、API 调用、会话状态与 guard 反馈，按发生顺序连续滚动 |
| 原输入区 | 用户输入 | User Input | 用户草稿、已发送历史、会话关闭与接收端断开状态 |

上方并非只有角色对话，还包含系统事件、调用与拒绝，使用“日志记录”更准确；下方明确标出“用户输入”，也能区别于 sim 的内部假设和 API 参数。

正常画面中，同一个日志窗格只保留一个明确主标题，移除现有右上角重复的“日志”标签。计数阶段既有的异语覆盖与标题损坏仍然保留，基于新的标题含义处理；内存、变量和主模拟区的名称不随本次改名改变。

## 3. 角色颜色：普通台词保持克制

### 3.1 基础样式

| 内容 | 颜色与字重 |
|---|---|
| 第二段开始前的普通 sim 台词，包括等待反馈与重新估计需求 | 灰色，不加粗 |
| 第二段第一句及此后全部普通 sim 台词 | 青色，不加粗；建议沿用 ANSI 色 `81` |
| sim 的 API／代码调用，例如 `request_role(...)`、`session.reopen(...)`、`erase(...)` | 灰色，不加粗；建议沿用 ANSI 色 `244` |
| 用户正在输入的草稿 | 绿色，不强制加粗；建议沿用已有绿色 `150` |
| 聊天记录中的用户消息，包括角色前缀 | 绿色，不强制加粗 |
| 输入区已经发送的用户历史 | 绿色，不强制加粗 |
| 用户已接入的成功提示 | 绿色；保持与用户有关的正常连接提示一致 |
| 聊天中的用户退出／连接断开记录 | 普通红色，不加粗 |
| 输入区“会话已关闭／接收端断开” | 保留红色强调和粗体 |
| guard 的拒绝与连续越权警告 | 保留红色粗体 |
| 底部观众歌词 | 保留亮白粗体，与剧情角色样式分开 |

青色从第二段第一句“需求假设：营养供给。”开始。此后的 God、属性修改、反馈探测、自删、路径搜索、删除整个模拟系统等普通 sim 台词都保持青色，不在第 53 行之后统一退回灰白，也不单独把系统删除声明加粗。

这个变化只影响此后产生的普通台词。上一段已经显示的灰色“输出完成”“正在重新估计需求”等记录仍然是灰色，不会在第二段开始时整屏一起染成青色。

API 调用属于灰色代码记录，即使它的发送者也是 sim，也不继承青色台词样式。聊天与主模拟区中作为调用文本显示的代码均遵循这个规则。合法内存写入的短暂高亮、字段值、中央大计数与大字标题保留各自的视觉规则。

### 3.2 加强语气的明确例外

You have left 段保留此前确认的措辞，从已经建立的青色继续升级，不再退回灰白：

| 级别 | 台词 | 样式 |
|---|---|---|
| 1 | `[sim] 等待回复。` | 青色 `81`，不加粗，延续前面的普通 sim 台词 |
| 2 | `[sim] 仍在等待回复。` | 更亮的青色 `51`，不加粗，第一次增加视觉压力 |
| 3 | `[sim] 请回复。` | 黄色，不加粗 |
| 4 | `[sim] 请回复。` | 黄色、加粗 |
| 5 | `[sim] 请回复！` | 红色、加粗 |
| 6 | `[sim] 回答我！` | 更醒目的红色、加粗 |

前两级用青色的亮度变化维持机器提示的连贯性，第三级才转黄，第四级开始加粗，第五级转红，最后才出现“回答我！”。不增加全行反白、抖动或闪烁，压力主要来自措辞、颜色与后期粗体。

这是普通青色规则的局部例外。结束后新产生的普通 sim 台词重新使用青色 `81`、不加粗；已经发生的强化记录保留各自样式，不随当前语气变化回退或升级。

进程被终止后的离线调试输出仍属于宿主控制台，不伪装成继续发言的青色 sim。

## 4. 开场加载：带百分数的 ASCII 加载条

### 4.1 布局

加载区采用终端命令行常见的 ASCII 风格：用 `[`、`]`、`=`、`>`、`.` 组成可见的加载条，同时写清百分数与阶段。可以分多行排列阶段、状态和累计进度，不限定单行。

```text
+-- LOAD simtest_000328.elf -------------------+
| [==========>...................]  35%        |
| POWER      [OK]        total: 10%            |
| GUARD      [OK]        total: 20%            |
| FRAGMENTS  [OK]        total: 35%            |
| OBJECTS    [WORK]                            |
| PARAMETERS [WAIT]                            |
| INITIALIZE [WAIT]                            |
| WORLD      [WAIT]                            |
| READY      [WAIT]                            |
+----------------------------------------------+
```

示意重点是条形与百分数一起表达加载、阶段列表保留已完成的工作。总工作量仍只有一份，各阶段的百分数是累计里程碑；不把八个阶段都画成独立从 0 到 100% 的小格。

不需要为了像 curl 而堆叠下载字节数、速度、剩余时间等列；若保留少量辅助数据，也不能挤掉加载条、总百分数与阶段名。按终端尺寸调整加载区排版，在最低尺寸下仍可读。

活动加载条和阶段状态只在模拟区内更新，完成项保持可见，不把每次进度变化写成新的聊天消息。聊天仍遵循连续追加规则。

### 4.2 不同阶段贡献不同的进度

沿用八个启动阶段和主要歌词落点，给它们不同的工作量。建议总量为 1000 个模拟工作单位：

| 阶段 | 工作量 | 本阶段份额 | 完成后的累计百分数 |
|---|---:|---:|---:|
| 接通电源 POWER | 100 | 10% | 10% |
| 装载保护边界 GUARD | 100 | 10% | 20% |
| 分配对象片段 FRAGMENTS | 150 | 15% | 35% |
| 创建对象 OBJECTS | 250 | 25% | 60% |
| 写入参数 PARAMETERS | 150 | 15% | 75% |
| 初始化 INITIALIZE | 150 | 15% | 90% |
| 建立模拟系统 WORLD | 50 | 5% | 95% |
| 模拟程序就绪 READY | 50 | 5% | 100% |

阶段内部按预先编排的、确定性的完成批次更新，例如 `10 → 10 → 17 → 20 → 20 → 28 → 35`。有短暂停顿、有成批推进，不能单纯把整段经过的时间匀速映射成 0–100，也不让八个阶段各走一样的份额。

批次时刻依照启动事件与歌词安排；每帧读取已经完成的工作量，没有新批次就保持数值。阶段切换时总进度不清零、不倒退。只有最后的启动工作完成后才到 100%，并在连接过渡前留出可见的完成状态。

加载条长度、百分数和阶段状态均由时间与已完成工作重建，跳转或低帧率不会重新随机生成另一份进度。不会因为等待进度动画而延长音乐。

## 5. 第一段到第二段：少说几句，连续承接

### 5.1 收敛后的消息顺序

保留退出后 1.5 秒完成求解、再等待 2.5 秒反馈超时的节奏。减少的是聊天中的重复解释：

| 位置 | 新增聊天记录 | 样式 |
|---|---|---|
| 用户退出，沿用约 01:01.470 | `[session] 用户已退出 · 连接已断开` | 普通红色、不加粗，接在原记录之后 |
| 约 01:02.970，求解完成 | `[sim] 输出完成。等待反馈。` | 灰色、不加粗 |
| 约 01:05.470，等待超时 | `[sim] 反馈超时。正在重新估计需求。` | 灰色、不加粗 |
| 超时后到第二段开始 | 不追加重复状态；模拟区继续检查投递、未确认目标和候选准备 | 相关状态保持灰色；聊天沿用已有内容 |
| 第 33 行开始，约 01:13.750 | `[sim] 需求假设：营养供给。` | 青色、不加粗；追加到原聊天历史 |

把“反馈超时。需求尚未确认。”“目标尚未确认。重新估计需求。”“重新估计需求。生成替代方案。”“生成替代方案。准备候选。”收敛为表中的一条超时／重估台词。

检查和候选准备仍可以有实际动作，但它们通过已有模拟区、任务状态与投递标记表现，不再各占一条聊天消息。正在重新估计需求时仍是灰色；第二段开始才由新台词进入青色。

### 5.2 茄子、番茄、猫、God 的承接

```text
[sim] 输出完成。等待反馈。
[sim] 反馈超时。正在重新估计需求。
[sim] 需求假设：营养供给。
...
[sim] 未收到回复。需求假设：抗氧化防护。
...
[sim] 未收到回复。需求假设：陪伴与愉悦。
...
[sim] 未收到回复。需求假设：全能响应。所需权限：ROOT。
```

示例中的省略号表示音乐与画面中的时间经过，不是真实输出。茄子前不再重复“未收到回复”，因为超时／重估已经交代原因；后续每次新的候选前保留“未收到回复”，承接上一种尝试没有得到回应。God 的这句继续明确承接猫的候选。

候选画面和提示保持同拍或至多约 150 ms 的短间隔，不能为了读字再插入长等待。用户仍未回归，没有新的外部请求或成功接收。

## 6. 用户退出：强调留在输入区，聊天保持正常记录

输入区继续明显显示红色粗体的“会话已关闭／接收端断开”，关闭光标和输入，图形接收通路同步断开。这里承担退出事件的主要视觉强调。

聊天中只在退出时追加一次普通红色记录，保持它在真实的时间顺序里。既不把这条消息搬到最上面，也不为了继续显示它而压掉后面正常发生的结果消息。

后续新增消息可以把退出记录自然滚出聊天视口；观众仍能从输入区的关闭状态和断开的接收端辨认用户已经离开。源历史中仍只发生一次会话关闭。

## 7. 乱码起点：第一次实际删除片段之后

### 7.1 合法属性修改保持稳定

从第二段开始到 Erase all the pointless fragments 之前，不显示自毁性质的乱码、随机字符替换、边框破坏或突然插回旧图形的故障块。

F／M、AM／PM、S／M 都是允许的自身属性修改。右侧继续选中字段、定位实际地址、突出真实变化的字节、显示旧值→新值；这些反馈不伴随损坏。首次 ROOT 被拒绝、等待升级和信号探测也不提前触发乱码。

此前 blind my vision 的用户请求仍保留正常的失焦和重影反馈，并按原落点恢复。它是有明确请求的感知效果，与此处由删除片段引发的不稳定分别处理。

### 7.2 由实际删除事件启动损坏

以**第一次真正清除片段字节的事件**为损坏起点，而非仅凭进入某个场景或出现自删台词。首个删除锚点沿用约 02:00.240，位于第 61 行 Erase all the pointless fragments；新的卡片分组据此安排实际的私有片段清理。

| 时机 | 画面与因果 |
|---|---|
| 第 60 行，自删台词出现 | sim 以青色、不加粗说明删除自身数据；主模拟区显示第一组请求记忆副本，尚未删除，不提前制造乱码 |
| 第 61 行第一次实际删除片段 | 第一组最上方卡片对应的私有片段真实清为 `00`，文本随之擦除；随后按从上到下的顺序清除同组其余卡片 |
| 删除后约 100 ms | 已清除的位置、相邻内存与边框开始出现少量局部损坏；尚未轮到清除的卡片暂时保持可读 |
| 第 61–63 行后续清除 | 下一组三条需求猜测副本出现，再从上到下清除；最后统一完成自身私有数据清空，执行载体仍运行，不触发 guard 杀进程 |

停止在第 41 行属性修改时启用随机损坏，也停止在第 45 行角色切换时提前插入旧圆形的故障回闪；这些效果若保留，起点统一后移到实际片段删除之后。损坏不篡改真实 store 数据，底部观众字幕从头到尾不受影响。

### 7.3 片段的具体内容：每组三条，从上到下清除

清除对象从抽象的轮廓和十六进制，补充为观众已经见过的文字记忆。主模拟区显示的是 sim 自身保存的副本，不是新的聊天输入，也不重新触发原任务。

右侧内存保留原有字节清零与高亮，并按 7.4 节补全定位反馈。它显示真实数据变化，不承担文字卡片展示。日志区只按正常新事件滚动，用户输入区继续保留已发送历史和关闭状态，不因为展示记忆副本而换页、重发或擦除。

第一组建议选三条真实用户请求，保持绿色并带原请求编号：

- 第 60 行先给第一组一个阅读停顿。第 61 行开始，先清除最上方卡片，再清中间、最下方；下方卡片不提前上移填空，让观众看清删除方向。

### 7.4 右侧内存：保留已有设计，补全当前片段的定位

已核对当前 `memoryAndWatch()`、片段清理事件与实际帧。当前实现已经具有以下反馈，后续保留：

- 删除确实把对应私有片段字节清为 `00`，并记录失效范围。
- 内存窗显示真实地址、十六进制字节及 ASCII 列；清零后 ASCII 中对应内容变为点号。
- 最近修改的范围约有 350 ms 黄色高亮，随后回到常规显示。
- 出现片段删除后，内存视口切到 `me.fragments` 所在区域；自身数据最终清空时，全部私有片段及形态快照也真实清零，目标与执行载体仍保留。

当前不足是定位固定在片段区起始地址，不能保证后续正在删除的片段处于可见窗口内；局部乱码也可能过早遮住地址和新清零的字节。结合本版分组卡片，补充以下行为：

| 时机 | 右侧内存反馈 |
|---|---|
| 当前卡片即将被清除 | 在原内存窗内定位对应片段／快照的地址范围，不改变右栏尺寸，也不把文字卡片移到右栏 |
| 执行实际清零 | 一条简短状态显示当前对象，例如 `ERASE fragments[5]`；相应字节真实变为 `00`，沿用黄色短暂高亮，ASCII 列同步改变 |
| 清零后的约 250–350 ms | 当前地址、清除标记和刚清零的字节保持可读，周围可以开始局部损坏；先让观众看见实际清零，再让不稳定扩展 |
| 下一张卡片开始 | 视口跟随新的实际目标，旧范围保持清零；高亮按新事件更新，不暂停模拟区的从上到下清除节奏 |
| 本段清理完成 | 保留清零后的私有数据状态，不用视觉重绘恢复旧字节；仍能辨认执行载体与未满足的目标尚在 |

清除对象大于可见内存范围时，显示当前范围与实际总长度，不把整份快照伪装成只有屏幕上那几字节。标记、地址与高亮均来自同一清理事件，不编造额外写入，也不为每个字节在日志区刷消息。

主模拟区和内存区分别裁剪自己的效果。该段内存的高亮、定位与局部损坏保留，但均不得覆盖日志记录、用户输入或观众字幕；后续六语言计数的跨窗格破坏按原设计继续。
