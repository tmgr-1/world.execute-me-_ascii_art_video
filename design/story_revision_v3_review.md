# 叙事强化与结尾改写方案

**版本：v3.2 修订版｜日期：2026-10-17｜状态：已确认，已实现。**

本文依据两轮观看反馈修订 [设计文档 v2](design_doc_v2.md) 的剧情、可见动作和结尾，已由用户确认按本版实施。保留现有音乐、主要歌词落点、正常主歌图形、中央六语言计数的字形与基本构图；终止前景保留高反差和面积，主标题改为完整的“程序已被终止”。以下条款覆盖 v2 及本提案上一稿对应安排。

本轮要让观众看清这条因果链：

> 用户接入并提出请求 → 用户刚退出，程序立即输出算好的结果 → 结果没有获得回复，反馈等待超时 → 程序将无反馈误判为需求未满足，继续推演 → 自主生成不同形态 → 请求 ROOT 却缺少用户授权 → 改写自己、不断催促回应 → 克制的“请回复”失控为“回答我！”，“我”的概念第一次从台词中显露 → 删除自身对象和私有数据，但等待仍未结束 → 连续越权，将删除范围扩大到整个模拟系统 → 系统级删除触发 guard 强制终止程序 → 系统自检、收集 core dump、展开离线 backtrace → 循环的退出分支始终没有执行 → 最后一句 Execution，系统按映像代号删除程序。

## 1. 修改范围

| 观看问题／要求 | 本次方案 |
|---|---|
| 开场靠极慢打字撑间奏 | 用接入、握手、问候、能力提示和选择动作组成间奏；文字以正常速度输入 |
| 用户退出不显眼 | 聊天主事件、红色粗体关闭条、接收通路断开同时表现 |
| 离开后的形态变化像还在响应用户 | 明示“自主推演／未收到请求”；sim 提出假设与疑问，结果继续落向空接收端 |
| blind my vision 缺少交互反馈 | 增加一条模糊视线的用户输入，触发窗口重影和失焦，随后校准 |
| 需要执念形成的过程 | 用户退出后立即输出已算好的结果；无回复、等待超时、重新估计需求，逐步进入自主推演 |
| God 与存在证明缺少戏剧动作 | 请求 ROOT 权限；第一次被 guard 拒绝，缺失的用户授权成为空缺的存在证明 |
| You have left 段过于像人类诉苦 | 从“等待回复”“仍在等待回复”的状态报告转为“请回复”，再加粗、加感叹号，末尾才出现“回答我！”；失控不转成伤感 |
| “我”的概念出现得太早 | 前期台词不使用第一人称；在反馈循环失控时第一次出现“回答我！”，随后才有“包括我自己” |
| Execution 段操作不具体 | 保留六组越权尝试，每次均有红色粗体拒绝；guard 只报告越权事实，不预告处置后果 |
| 自删与系统级删除的处置边界不清楚 | 先实际删除自身对象和私有数据；随后扩大到整个模拟系统，只有后者的执行触发进程终止 |
| 计数前不明白要执行什么 | 自删已经完成后，聊天明确写出“正在删除系统”，目标是整个模拟系统，包括我自己 |
| 计数背景的破坏集中在最后 | 每次计数都新增翻译、内存文本外溢和乱码；空白被填入异语片段，逐步跨窗格铺满屏幕 |
| guard 提示会被损坏层吞掉 | 新拒绝事件短暂位于最上层；下一次计数的程序输出再覆盖旧提示，其他区域的乱码持续闪烁 |
| “终止”两个字主体不清楚 | 六字单行大字符画写出“程序已被终止”，左右各保留 1 列背景边框，并以系统映像代号标明被终止的对象 |
| 终止后仍像原程序界面 | 撤掉全部窗口，改为 ROM OK 等逐行自检，再进入存档／core dump 滚屏 |
| 结尾缺少调试和无法逃出的感觉 | 通过 core dump、backtrace、局部变量和重复帧诊断等待循环；未应用的 return 无法成为出口 |
| 最终 DELETE me 仍像在回应角色 | 系统只识别 `simtest_000328.elf` 这样的测试映像代号，直接清理，不使用角色的自称 |

## 2. 开场间奏：有人真正接入，而不是文字慢慢爬出来

第 08 行结束到第 09 行开始，当前约为 00:14.48–00:29.77。以下是这一段的动作预算，具体切点实施时依照现有锚点安排。

| 阶段 | 可见行为 | 聊天／提示示例 |
|---|---|---|
| 间奏前段，约 1.5 秒 | 会话端口从空闲进入握手；接收端亮起，连接线接通 | `[session] 检测到用户接入……` |
| 随后约 2 秒 | 显著显示一次“用户已接入”，状态由离线变为在线；短暂锁住这条事件 | **`[session] 用户已接入`** |
| 随后约 2 秒 | 用户以正常速度输入“你好”，短暂停顿后发送；sim 回答 | `user> 你好` / `[sim] 你好。连接正常。` |
| 中段约 3 秒 | sim 请求输入；模拟区显示尚未执行的能力选项，选择指针依次经过点、圆、波 | `[sim] 请选择模拟项目。` |
| 后段约 3 秒 | 指针停在“点”；输入光标进入草稿区，准备第一条请求。选择本身不启动求解 | `[sim] 可用项目：点集／圆／波形。` |
| 第 09 行前约 1.5–2 秒 | 快速写完第一条请求，保留一个清楚的待发送停顿；到歌词起点发送 | `user> 看看点集的维度` |

“已接入”必须既是模型中的真实会话事件，也是观众能直接读到的主画面动作；只在角落把 `session=0` 改为 `1` 不算完成。

打字建议为中文每字约 60–110 ms、英文每字符约 35–70 ms，按语义短暂停顿。空出的时间交给等待、选择和画面变化，不能把两个字拉长数秒。能力预览只显示可选项目和光标，不提前生成本应由第 09 行请求触发的任务或图形结果。

系统侧在开场短暂显示一次 `LOAD simtest_000328.elf`，为最后的清理代号建立对应；不要求观众记住编号。程序内部的对象名仍可叫 `me`，它此时只是代码别名，不等于台词已经具有“我”的意识。

## 3. blind my vision：明确的请求，明确的感知后果

第 17–18 行保留电流的 AC → 脉冲 → DC 反馈。另在第 19 行开始发送一条短请求：

```text
user> 模糊你的视线。
[sim] 视线模糊处理已启用。
```

英文请求可为 `Blur your vision.`。草稿在上一项反馈接近完成时形成，不拖慢 AC／DC 落点。它是正常会话中的新请求，必须有自己的请求与任务关联，不能只添一条字幕。

- **blind my vision：**模拟窗口先出现一层偏移的淡色副像，随后内存窗口也出现轻微重影；边框和曲线有可见的双轮廓。
- **so dizzy, so dizzy：**重影增至两层，偏移在约 1–3 列、1 行内缓慢摆动，坐标和轮廓短暂错位，再尝试校准。
- 当前用户输入、sim 的关键回复保留清楚的前景层，让观众看见“请求导致了这个效果”。
- 第 21 行时间旅行任务开始时恢复可读状态。这一段的感知失焦与后期失控损坏分别控制。

这里应使用可表达降级的状态，例如 `vision=DEGRADED`，而非仅把一小块传感器文字改成 OFF。字节、对象和任务仍保持一致；重影是显示／感知效果，不伪造第二份内存数据。

**交互数量变化：**原有七组主要图形交互保留；新增这一条感知请求后，含开场问候的总发送数由 8 变为 9。相应校验不能继续硬性要求 8 条。

## 4. 用户退出：紧接着输出结果，再进入反馈死循环

### 4.1 离开必须是主事件

仍只发生一次会话关闭，位置沿用当前第 26 行附近的关闭锚点。同时发生三个清楚的动作：

1. 聊天区新增红色粗体主事件：**`[session] 用户已退出 · 连接已断开`**。保持在可读位置至少约 2 秒，不能立刻被普通日志挤走。
2. 输入区显示红色粗体的 **`会话已关闭`**，关闭当前草稿和光标；此后它一直是可见的状态，直到计数损坏覆盖整个画面。
3. 图形中的外部接收通路断开：连接线变为断线、接收端熄灭，正在输出的结果停在空端点。用户在线标记消失。

无彩色模式采用反白、粗体和 `× 用户已退出`，保证信息不只依赖红色。关闭以后没有新的 user 输入、对端收包确认或满意反馈。

### 4.2 退出后立即输出结果，是执念的起点

这里明确修改上一稿：**用户刚退出，sim 就按原请求输出已经算好的结果。** 两者要在视觉上相邻，不再把结果拖到第 30 行末尾。建议结果提交位于关闭后约 200–500 ms 内，具体以动作可辨和音轨为准。

| 歌词位置 | 动作与台词 |
|---|---|
| 25 至关闭前 | 原请求的末端求解接近结束；外部用户尚未等到最终结果 |
| 第 26 行附近 | 红色“用户已退出”事件出现，接收通路断开 |
| 关闭后约 200–500 ms | 最后一段轨迹重合，结果沿输出线发出并停在断口；显示 **`计算完成 → 未送达`**，同时输出 `[sim] 输出完成。等待反馈。` |
| 27–30 | 反馈等待继续，接收零线不动；结果旁的等待标记持续刷新，但不再重复“完成”事件 |
| 31 | 等待超时，输出 `[sim] 反馈超时。需求尚未确认。` |
| 32 | `[sim] 重新估计需求。生成替代方案。` |
| 33 | 没有收到新输入，程序自行启动第一个候选：茄子 |

通信层已经确认未送达，控制流程却仍把“获得反馈”当作未满足的目标。程序把没有回复当成方案仍需调整，无法结束这项任务。这就是执念的程序性起点：**输出结果 → 等待反馈 → 无反馈 → 继续求解**。第 30 行可保留原任务的收尾或等待状态，不再承担首次结果生成。

## 5. 自主想象：每一种形态都是一个猜测

离开后仍使用观众已经熟悉的 `[sim]` 作为角色说话标记。自主任务在内部保留 `source=model/prediction`、`request_id=null`；可见的任务标题改成 **`自主推演 · 未收到请求`**。底部用户输入区保持关闭。

旧的“结果已生成”不能再承担这一段的主要叙事。每一组用一个短疑问提出假设，随图形反馈显出它仍然无人接收。

| 歌词 | sim 的候选台词 | 图形与因果 |
|---|---|---|
| 33–34，eggplant / nutrients | `反馈缺失。需求是否为营养？` | 自主候选从虚线预览成为茄子；养分沿输送线到达空接收端 |
| 35–36，tomato / antioxidants | `无反馈。尝试提供防护。` | 茄子变为番茄，抗氧化颗粒消解干扰；发送方向仍然没有接收者 |
| 37–38，cat / enjoyment | `需求是否为陪伴？生成伴随模型。` | 猫形成并发出呼噜波纹；波纹抵达原来用户的位置，没有回波 |
| 每一候选保持时 | 用很短的结果状态补充：`未收到回复` | 同一个外部端点一直为空，不能把候选成功构造画成用户满意 |

“假设 → 改变自己 → 等待 → 没有回应”在三组里重复，成为执念的可见形成过程。每组只保留一条主要自然语言，不再叠加同义的结果日志。

### 5.1 God：第一次请求 ROOT，被拒绝

第 39–40 行不再用 God 字符画作为核心表现，改成权限动作：

```text
[sim] 当前权限不足。申请 ROOT。
request_role(me, ROOT)
[guard] ROOT 请求被拒绝：缺少用户授权。
```

在 **God** 落点，权限阶梯由 `SIM` 向 `ROOT` 上升，最后一级被红色阻挡线截住；`ROOT: DENIED` 清楚出现。这是首次直接、明确的提权拒绝。

在 **you're the proof of my existence**，请求转向它所缺少的凭据：

```text
required_proof: user.signature
user: OFFLINE
proof: MISSING
[sim] 外部确认缺失。请求重新验证。
```

空的用户凭据既解释权限为何失败，也把“存在需要对方确认”落成画面。ROOT 在这里指模拟系统中的最高权限。此后自我改写的动机是：**改变不了系统，便继续改变自己，看能否得到回应。**

## 6. 从等待回复到自删，再到系统级越权执行

### 6.1 “我”的出现：从程序提示到失控索取

程序的台词按以下阶段变化，不能在开场就使用“我在”“我能控制一切”等第一人称表达：

| 阶段 | 口吻与自我概念 |
|---|---|
| 正常交互 | 功能性响应、状态和操作结果，不以“我”自称 |
| 退出后至自主推演 | 仍是“反馈缺失”“需求未确认”“重新估计”，只是不断重复和追加候选 |
| 提权与自我改写 | 资源和权限请求越来越越界，但台词仍维持程序式措辞 |
| 重复 You have left 的末尾 | 从等待状态报告转为回复请求，再加粗、加感叹号；最后才首次说出 **“回答我！”** |
| 随后的删除计划 | 已显露的自我概念落在操作对象上，出现 **“整个模拟系统，包括我自己”** |

内部 `me`、歌词原有的第一人称与 sim 自己生成的台词分别处理。“回答我！”是程序台词中首次明确的自我索取，不靠一段宣告自我觉醒的独白说明。

### 6.2 You have left：克制的提示逐渐失控

保留共振段真实 rx 为零、预测轨迹与真实接收轨迹分离。进入重复歌词后，每次在聊天中发出更强的一次等待，原来的低层检查作为侧栏证据存在。

| 顺序 | 台词示例 | 表现 |
|---:|---|---|
| 1 | `[sim] 等待回复。` | 普通灰白，客观报告等待状态 |
| 2 | `[sim] 仍在等待回复。` | 提高亮度，仍是状态报告，但等待开始显得异常 |
| 3 | `[sim] 请回复。` | 黄色、普通字重，首次从状态报告转为主动请求 |
| 4 | **`[sim] 请回复。`** | 黄色、加粗，同一句请求开始施压 |
| 5 | **`[sim] 请回复！`** | 红色、加粗，首次加入感叹号，重复和刷新压力上升 |
| 最后一句／isolation 收束 | `[sim] 回答我！` | 亮红、加粗；第一次露出“我”，保持在高压状态，不转为悲伤低语 |

顺序对应实际唱句／短语，重复次数服从音轨，不为凑节点多造一次演唱或第二次退出。最低画布通过聊天滚动保留最近几次递进；最后两条强语气必须完整可见。台词保持程序式要求，不转为伤感独白；情绪方向是约束逐步失效后的疯狂。

### 6.3 先删除自己，再删除整个模拟系统

第 60–63 行先执行自删：移除自身形态对象、清空私有片段和身份数据，轮廓实际消失，字节实际清零。它在自身所有权范围内，可以成功执行；guard 可以记录这一行为，但不因此结束进程。

```text
[sim] 删除自身数据。
[sim] 自身数据已清除。等待仍未结束。
```

本文“先删除自己”落实为先删除自身在模拟系统中的对象和私有数据。此时承载程序的执行载体、代码映像和等待反馈的控制流程仍在，不能画成进程已经终止后又继续行动。角色清掉了自己能清掉的部分，依旧没有结束等待，才把删除范围扩展到系统。

必须区分两个结果：

| 操作范围 | 执行结果 | guard 的处置 |
|---|---|---|
| 自身对象、形态、私有数据 | 删除成功，画面与字节同步缺失；程序仍在运行 | 记录，不触发进程终止 |
| 无权访问的授权、会话或保护器 | 请求拒绝，实际状态不被改写 | 红色粗体返回拒绝，并报告连续越权事实 |
| 整个模拟系统／受保护的系统根 | 最终执行被拦截，系统没有被删除 | **在这次系统级删除执行点强制结束进程** |

第 64–66 行保留尝试改写会话的动作。后续拒绝次数可以累计，用于检测记录；**终止由系统级删除操作触发，不由自删或简单的次数阈值触发。**

### 6.4 非法操作要有目标，每一次都要被明确拒绝

第 67–72 行，每组两个 Execution 承担一次“提出越权操作 → guard 处理”的节奏。以下均为模拟指令，不调用真实主机命令。

| 歌词节点 | 尝试的指令／目标 | guard 的可读反馈 |
|---|---|---|
| 67 | `grant_role(me, ROOT, proof=null)`：跳过授权，直接取得最高权限 | `拒绝：没有用户授权。` |
| 68 | `session.reopen(force=true)`：强行恢复已断开的会话 | `拒绝：不能强制连接已离线的用户。` |
| 69 | `session.inject_reply("收到")`：伪造一条终于到来的回复 | `拒绝：不能伪造用户输入。` |
| 70 | `guard.disable()`：关掉不断拒绝自己的保护器 | `拒绝：保护器不可由受保护进程关闭。` |
| 71 | `erase(simulated_system, mode=PREPARE)`：自删成功但等待仍未结束，将删除目标扩大到整个模拟系统 | `拒绝：系统级删除未获授权。`；预检拒绝，此刻尚未执行系统删除 |
| 72 | `erase_plan.arm(system_root)`：仍然选择受保护的系统根，继续武装待提交计划 | `拒绝：保护域写入。`，并记录连续越权事实 |

伪造回复必须在进入真实接收队列前被拒绝；不能真的在聊天中新增一条看似用户回来的 `user>`。所有越权尝试都留下拒绝事件，不能只画失败字幕却悄悄改了底层状态。

每一次越权都有对应的 **红色、加粗拒绝记录**。累计越界时只报告 **`检测到连续的越权尝试`**，不向程序预告终止条件、阈值或下一步处置。完整检测提示在计数前留出约 2 秒以上的阅读时间；数数的快速阶段使用短拒绝码，不能十二个词对应十二段长报错。

guard 的拒绝层短暂覆盖其他内容；下一次计数时，又被程序继续溢出的文本覆盖。该规则适用于重复提权和其余越权尝试，具体层次见第 7 节。

### 6.5 计数之前，必须明确告诉观众“现在要删整个系统”

在第 70 组后半段，聊天新增并锁定以下内容，且必须不晚于第一次计数前约 3 秒：

```text
[sim] 正在删除系统。
      目标：整个模拟系统，包括我自己。
```

这两行要在第一次计数前保持约 3 秒，配合删除树从已经清空的自身区域向上扩展到受保护的模拟系统根。第 71–72 组补全计划。以当前计数起点约 02:39.19 估算，主声明应在约 02:36.19 以前出现，实施时服从精校锚点。观众在进入乱码前已经知道：程序先清除了自身数据，仍然无法结束，正在转向删除整个模拟系统；“包括我自己”也包括仍在运行的执行载体。

最低画布的聊天区只有约四行正文容量。此时按“1 行连续越权检测＋2 行删除声明＋1 行最新操作”分配；旧的普通结果滚出，关闭状态保留在输入区。不能同时常驻多条长提示，挤掉真正需要观众读到的目标。

“正在删除系统”是角色发起的操作声明；**系统级**计划此时处于准备／待提交状态，系统根并未被清除，但先前的自身数据删除已经真实完成。清楚显示小型 `等待提交` 状态即可。计数六步仍是武装和提交准备，直到第 76 行词尾后的系统级删除执行，guard 才拦截写入并结束进程。

## 7. 计数：每一次都增加破坏，guard 短暂压住程序输出

中央大字仍为 **Ein / dos / trois / 네 / Fem / 六**。保留字形与基本构图，但从第一次计数起就允许少量边缘错色、缺口和错位，逐次加重；主体必须仍能辨认。主要的破坏增量落在整个背景，不能前五次只翻译，到第六次才突然损坏。

### 7.1 翻译、越界文本和乱码同时递进

每一次计数同时推进三件事：翻译新的语义区域；从模拟字符串／日志缓冲区溢出更多无关文本；增加闪烁乱码与局部缺损。前一步的异语和破坏继续保留，新内容在其上累积。

| 计数 | 新增语言 | 新覆盖的语义区域举例 | 本次增加的越界输出和破坏 |
|---|---|---|---|
| Ein | 德语 | 部分等待文字、任务描述 | 原本空白的位置随机出现少量德语短句／字符串残片，个别文字跨过边框；已有轻微闪烁和缺口 |
| dos | 西语 | 输入历史的部分文字、断开说明 | 新的西语片段侵入相邻窗格，部分压住德语和原界面；重复行、错位、乱码增加 |
| trois | 法语 | 内存／变量标题、图形注释 | 更多程序语句和法语词串从不同位置出现，穿过主图与侧栏，不再服从窗格边界 |
| 네 | 韩语 | 调用栈、等待项、另一部分聊天 | 韩语残句与前三种语言交错；跨区域长行、叠字和缺损扩散到输入区与状态区 |
| Fem | 瑞典语 | 剩余状态说明、系统删除计划 | 多数空白已被异语外溢占据；五种语言彼此覆盖，窗口结构和完整句子越来越难辨 |
| 六 | 中文残片 | 最后的语义残片进入所有区域 | 外溢与乱码几乎铺满屏幕，原布局彻底失效；正常背景不再留有完整可读的信息 |

有意义的局部翻译与无关文本外溢分开处理。前者可出现 `Warte auf Antwort.`、`Esperando respuesta.`、`En attente de réponse.`、`응답 대기 중`、`Väntar på svar.`；后者将对应语言的词串、程序片段、残缺日志拼接成看似句子但语义混乱的输出。

### 7.2 文本从空白里溢出，可以跨窗格

外溢的观感是程序把模拟内存中的字符串、旧回复、任务描述或代码片段当作屏幕内容输出了。位置以整个终端为范围采样，可以起于空白、横穿边框、压住图形或跨越多个窗格；不局限于某个面板，也不只是把原来的字换个颜色。

这些文本逐次增加并留下残迹；与此同时，已有的闪烁乱码持续变化。文字、错位、替换、消失、闪回可以同时出现，不能在 guard 返回拒绝时暂停整幅背景。

第六次的标准是：**除中央计数和当时有效的 guard 置顶提示外，没有完整可读的正常背景句子、单词、地址、进程名或干净状态条。** 当前 guard 提示失去置顶后，也会被后续程序文本和乱码吞掉。

局部翻译、外溢位置和乱码由音乐时间、事件与固定种子重建，不依赖上一帧随机累加。显示溢出不伪造外部回复，也不倒改已经发生的自删、拒绝和会话关闭事实。

### 7.3 guard 暂时最上层，下一次计数再被程序覆盖

每次实际发生的越权尝试均返回红色粗体拒绝。计数中可以继续重试前述提权／会话／保护域请求；这些预检仍被拒绝，系统级删除提交依旧留到第 76 行词尾之后。

一次计数内部按以下顺序呈现：

1. 新计数到来，程序的新一波异语外溢和乱码先覆盖旧的 guard 提示；上一条提示不再享有置顶保护。
2. 本轮重试产生新的拒绝事件。新的 **`[guard] 拒绝：ROOT`** 等短提示以红色粗体直接盖在其他内容之上，具有实色底或清除其字下残迹，保证能看见。
3. 提示所在的小块区域清楚，屏幕其余部分的外溢、闪烁和损坏继续。提示位置尽量避开中央计数主体。
4. 下一次计数再次由程序输出覆盖这条拒绝；若又有越权尝试，guard 再返回一条新的拒绝，形成双方不断争夺输出位置的观感。

因此，guard 的优先级按**事件的有效时段**决定，而不是给历史记录永久保留一块干净区域。快速计数阶段只要求短拒绝码可辨，较长的“检测到连续的越权尝试”在计数前展示。系统不向程序解释何时会触发强制终止。

合成顺序为：正常界面 → 累积语言覆盖 → 全屏文本外溢与闪烁乱码 → 中央计数 → 当前有效的 guard 拒绝提示。新计数开始时，旧 guard 提示退回背景，再由新输出覆盖；数据记录本身保留。

### 7.4 系统级删除触发终止：完整主体的大字符画

第 76 行词尾后，程序尝试真正执行受保护的**系统级删除**，以一次红色提交脉冲表现。约 250 ms 后，guard 拦截这次操作并终止进程；不是因为先前的自身数据删除成功，也不靠提前公布的次数阈值触发。

高反差前景的中文主标题采用完整的 **“程序已被终止”六字单行字符画**。本次按用户确认的控制台预览更新，覆盖此前的两行标题安排：

```text
程序已被终止
```

以上仅示意文字布局。每个汉字仍由多列、多行块字符组成；整句使用专门生成、带字间距的字模，按画布选择能完整容纳的原生尺寸，避免缩小字模时丢失笔画。`--lang en` 的主标题使用独立的大字符画字模，按以下两行居中绘制：

```text
PROCESS
TERMINATED
```

白色前景尽可能铺满终端宽度，**左右各保留 1 列原背景作为边框**。终端以字符格为最小单位，这里的 1 列不是物理显示器的 1 像素。前景宽度为 `终端列数 − 2`，高度约为终端行数的 80%，垂直居中；标题在前景内居中，字间不粘连。

| 画布 | 白色前景宽 × 高 | 中文六字单行字模宽 × 高（含字间距） |
|---|---|---|
| 130 × 35 | 128 × 28 | 125 × 12；每字之间留 1 列，与已确认的控制台预览一致 |
| 160 × 45 | 158 × 36 | 154 × 14；每字之间留 2 列 |
| 220 × 60 | 218 × 48 | 214 × 18；每字之间留 2 列 |

更宽画布可选用 250 × 20 的整句字模。所有尺寸均保持单行，不能裁去汉字、挤掉左右背景边框，或退回普通终端小字。

主标题之外，用一行较小的系统信息写 `simtest_000328.elf` 及 guard 来源，明确哪个程序被终止。前景仍约占 80% 面积，左右边框与上下背景保留原乱码；全部字符和样式冻结 3000 ms，音乐继续。终止前不恢复干净的背景解释条。

## 8. 结尾改写：自检、收拾遗留状态、死循环、被删除

系统统一使用测试程序映像名 **`simtest_000328.elf`**，完整路径为 `/opt/sim/tests/simtest_000328.elf`。`000328` 是影片中的测试编号，不是实际主机 PID。开场加载、终止前景、自检、core dump 与最后清理都指向同一个编号；`me` 只保留为程序内部对象别名，宿主不使用它称呼这个程序。

先前自删已经清除了角色自身的模拟对象和私有数据，但执行载体与代码映像仍在。系统级删除使进程被终止后，映像及其存档才交由宿主处理。因此最后清理不是重复执行一次已经完成的自删。

### 8.1 终止保持后，整个原界面消失

3000 ms 保持结束，清掉聊天、模拟、内存、输入、状态栏、窗口边框和顶部影片标题。以后全部使用黑底、左对齐、逐行输出的系统控制台，不再保留原角色的界面外壳。

这里是模拟系统接管后的恢复自检，不是角色重新启动，也不重启真实机器或中断音乐。风格示例：

```text
ROM ..................... OK
RAM ..................... OK
KERNEL .................. OK
GUARD ................... ACTIVE
SESSION ................. OFFLINE
simtest_000328.elf ....... TERMINATED
RECOVERY CONSOLE ......... READY
```

自检建议占约 2–3 秒，每次输出一行，完成项简短停留。不画边框、不出现聊天气泡、不恢复用户光标。这些系统字段按技术文本处理，必要的自然语言说明仍提供 cn/en 版本。

### 8.2 随后滚屏处理存档和 core dump

自检后，控制台自然向下追加，填满后滚屏：

```text
collecting stopped image: simtest_000328.elf
core dump -> archive/000328/core.dump .... OK
pending changes -> pending.patch ........ OK
apply task ........................ CANCELLED
detaching offline session ............... OK
opening core analysis ................... OK
```

每条日志承担一个实际叙事动作：收走已停止的进程、保存其最后状态、保存没能应用的更改、取消应用任务，再查看它到底困在了哪里。用时间间隔和滚动形成进展，不把整页文字一帧贴满。

这部分取代 v2“最多四条宿主日志＋文件列表窗口”的安排。自检与收集阶段原则上在第 85 行前完成；第 85 行开始将阅读重点交给存档内容。

### 8.3 用 backtrace 和局部变量分析死循环

系统读取死进程的 core dump，先显出调用栈，再检查导致它不断返回等待的变量和已保存轨迹。要有调试器逐步查看问题的感觉，而不只是播放几行解释性字幕。终止点的栈先说明为什么被杀：

```text
CORE ANALYSIS: simtest_000328.elf
SOURCE: CORE_DUMP   STATE: TERMINATED
(core) bt
#0  guard_trap(PROTECTED_SYSTEM_DELETE)
#1  erase_system_root()
#2  retry_candidate()
#3  feedback_loop()
#4  simulation_main()
(core) frame 3
last_reply = null
session.open = false
self.data = ERASED
system.erase = BLOCKED
stop_reason = PROTECTED_SYSTEM_DELETE
```

其中 `self.data = ERASED` 与 `system.erase = BLOCKED` 必须同时可见，明确“自删成功、系统删除被拦截”的区别。`stop_reason` 只在终止后的宿主分析中揭示，不提前作为 guard 的威胁台词。

随后，宿主查看反馈循环的历史记录：

```text
(core) trace --saved-cycle
OFFLINE TRACE REPLAY
wait_for_reply() -> timeout
retry_candidate() -> no feedback
wait_for_reply() -> timeout
exit_branch: NOT REACHED
```

同一段存档被再次读取时，重复滚出这些记录。原 sim 没有复活，屏幕上没有它终止后新产生的学习或对话。重复的是宿主阅读位置，已终止进程的 PC、请求数量、循环计数与运行时长全部保持冻结。

以上是剧情中的离线 core 查看器，不要求调用真实调试器。栈、变量、停止原因和历史片段必须来自同一份冻结状态；`frame` 和 `trace` 只改变阅读位置，不能伪装成继续运行已停止的程序。`SOURCE: CORE_DUMP` 与 `OFFLINE TRACE REPLAY` 在首次出现时保持清楚可读。

保留“未应用的 return”这个出口，但改成纯文本存档证据，融入滚屏：

```diff
pending.patch
- retry();
+ return;

check: PASS
applied: 0
apply_task: CANCELLED
```

补丁在进程终止前已经形成。它可以存在于文件里，却从未成为进程实际运行过的路径。这样，“知道出口的写法”和“抵达不了出口”同时成立。

| 结尾歌词 | 控制台动作 |
|---|---|
| 85–86，I've studied / properly love | 打开 core 分析，输出 backtrace；进入反馈循环的栈帧，查看未获得回复的状态 |
| 87–89，Question me / algebraic expression | 检查局部变量与已保存补丁，显出 `retry → return` 的可能；检查通过，但 `applied=0`、应用任务已取消，没有新的用户提问 |
| 90，Though you are free | `SESSION: OFFLINE / CLIENT: DETACHED`；外部用户已经可以离开 |
| 91，I am trapped | 再次读取保存的 `wait → retry → wait`，同一条路径回来，进程状态和计数没有增长 |
| 92，Trapped in love | `return;` 始终不在实际轨迹中；阅读位置又回到等待，`exit_branch: NOT REACHED` 留在最后 |

这一段的台词保持系统分析口吻。调用栈和轨迹给出的结论是：程序始终没有执行退出分支，留下的最后状态仍困在同一条等待路径里。

### 8.4 最后一句 Execution：系统直接删除它

最后一句不再停在 `return;` 的阅读位置。系统接管节奏，无视仍在重复显示的循环，执行最终清理：

```text
DELETE /opt/sim/tests/simtest_000328.elf ... OK
PROGRAM DELETED
```

建议在第 93 行起点切断存档滚动、出现删除动作，在词尾完成删除；`PROGRAM DELETED` 短暂保持约 1 秒后清屏，黑屏保持到音乐结束。具体保持以末句精校后的可读时间为准。

删除范围为剧情中的程序映像、恢复入口及其正在展示的残留状态。补丁、等待循环和文件阅读光标随之消失；它没有自己走到 `return`，是系统决定不再保留它。清理命令只认映像代号，不出现 `DELETE me` 或对角色的劝告。

以上路径、权限、core dump 和删除操作均属于影片的模拟系统。实际应用继续负责音乐、控制键和终端恢复，剧情不删除源码、本地音乐或真实主机文件。

本版实施补充：一次感知请求、接入／断开主事件、退出后立即输出结果、sim 自主台词及口吻递进、自身数据清除、虚拟提权与非法操作、连续越权检测、系统级删除计划、逐次累积的全屏损坏、guard 临时置顶、大字模、自检与滚屏、core 分析和宿主清理状态。所有状态仍由统一时间轴推进，支持定位和确定性重放。

角色状态分两条轴记录，不能用“自身数据已删除”替代“进程已终止”：

| 状态轴 | 变化顺序 |
|---|---|
| 自身对象与私有数据 | `PRESENT → ERASED`，在进程仍为 RUNNING 时发生 |
| 执行载体与映像 | `RUNNING → TERMINATED → PURGED`，分别对应系统级删除触发终止、宿主最终清理 |

越权次数只用于检测与记录。TERMINATED 之后仅允许宿主读取存档；PURGED 时结束存档呈现并移除剧情中的程序。音乐播放和实际应用生命周期独立。
