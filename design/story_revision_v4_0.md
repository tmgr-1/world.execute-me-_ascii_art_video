# v4.0 剧情节奏、提示与字幕分层设计

**版本：v4.0｜日期：2026-10-17｜状态：已确认，已实现；自动检查通过，实机观看待复核。**

本文以当前 v3.2 实现和本轮观看反馈为基线，修订加载提示、用户退出后的节奏、第二段的机器台词、Execution 与 guard 的显示顺序，以及全程歌词的显示方式。本文覆盖 [v3.2 修订版](story_revision_v3_review.md) 和 [设计文档 v2](design_doc_v2.md) 中与本版冲突的条款；未涉及的剧情与交互继续沿用。

本版已按审阅后的条款实现，包含 4.3 节补充的“未收到回复”承接台词。时间按现有音轨锚点安排；不改动音乐、不整体重做歌词校准。用户提供的音乐仍只通过 `--music-file` 传入。自动检查与关键帧检查见 [实施与验收记录](../docs/acceptance.md)，实机完整观看和听音复核仍由后续排演确认。

## 2. 开场加载：用百分数表达实际阶段进度

保留原有八个加载阶段及其歌词落点，包括供电、guard、片段、对象、参数、初始化、系统与模拟程序就绪。把加载标记中的 `##`、点阵填充等改为百分数。

```text
LOAD simtest_000328.elf
[100%] 供电检查
[100%] guard 初始化
[ 62%] 加载模拟对象
[  0%] 参数初始化

模拟程序加载：037%
```

- 百分数来自当前阶段的确定性进度；完成项保持 `100%`，未开始项为 `0%`。
- 总进度单调递增，在最后一个阶段真正就绪时到达 `100%`。它表示模拟程序的启动进度，不表示音乐下载进度或真实主机资源检查。
- 仍由歌词推动阶段切换；不为了跑满百分数延长开场，也不把正常文字输入拖慢。
- 后续接入、问候、选择、第一条请求继续沿用 v3.2 的动作安排。

### 3.2 因果保持不变

程序先完成原请求，结果没有送达，也没有收到回应。它将“没有回应”推断成“需求仍未满足”，于是开始生成替代方案。后续没有真实用户输入，也没有成功收到确认。

退出主事件在首次结果出现后仍应留在聊天可读位置；不能由普通状态行立即挤走。红色粗体的“会话已关闭”持续保留，直到后期剧情损坏覆盖输入区域。

## 4. 第二段：减少重复，用机器台词解释每个动作

### 4.1 候选假设合并成一句

每一组形态只在开始时输出一条主台词，把无回应事实和候选解释合并。删除同一候选末尾再次输出的“未收到回复／无反馈”；图形和接收零线继续说明无人接收。

| 歌词位置 | 中文主台词 | 图形与状态 |
|---|---|---|
| 33–34，eggplant / nutrients | `[sim] 未收到回复。需求假设：营养供给。` | 自主生成茄子，养分输出至空接收端 |
| 35–36，tomato / antioxidants | `[sim] 未收到回复。需求假设：抗氧化防护。` | 生成番茄与抗氧化效果，接收量仍为零 |
| 37–38，cat / enjoyment | `[sim] 未收到回复。需求假设：陪伴与愉悦。` | 猫与呼噜波纹形成，外部没有回波 |

三句是不同方案的起点，不在同一组内拆成两句重复报告。内部任务日志可以记录开始、捕获和返回，但不得再以普通聊天消息覆盖上述主台词。

主台词在对应歌词起点一次显示，候选画面在同一拍开始，最多稍后约 80–150 ms。不等待完整打字动画，也不单独留出数秒让观众先读台词；这条节奏同样适用于后面的自身属性修改提示。

这一段继续使用 `source=model/prediction`、`request_id=null`。没有模拟成用户新发的指令；输入区也不能重新打开。

### 4.2 让 sim 的关键输出有稳定视觉焦点

第 33–52 行的上述假设、ROOT 动机、属性修改和探测提示使用**亮青色、粗体**，建议 ANSI 256 色 `81`。角色标签 `[sim]` 与正文一起突出；技术元数据保持暗色。每组动作的主台词留在聊天可读区域，避免内部日志抢占。

guard 保持红色粗体，形成不同的角色颜色。第 53 行开始的等待升级继续使用原有灰白→亮白→黄色→红色递进，不被本段青色规则覆盖。无彩色模式通过粗体和留白维持焦点。

### 4.3 God：把“全能”转译为最高权限

动机直接来自第 39 行“If I'm the only God”，并延续前面不断尝试满足用户需求的逻辑：茄子、番茄、猫只是局部能力，程序进一步提出“全能响应”的候选。它把 God 理解为能控制全部模拟规则、提供全部模拟能力的唯一最高权限持有者，因此申请 ROOT。这里不以重建反馈通路或重新连接用户作为提权理由。

```text
[sim] 未收到回复。需求假设：全能响应。所需权限：ROOT。
       request_role(me, ROOT)
[guard] 拒绝：缺少用户授权。
[sim] 授权证明缺失：用户确认。
```

开头的“未收到回复”承接上一组猫／陪伴候选也没有获得回应，因此程序继续提出全能响应假设；不在猫段末尾另加一条重复报告。第 39 行先出现这条合并台词，紧接着提交申请、显示第一次拒绝。主模拟区用 `capability=ALL → role=ROOT` 表示候选能力与所需权限的关系，不新增字符画神像。申请与拒绝不为等候读字而拖到下一句。

第 40 行“you're the proof of my existence”时才输出“授权证明缺失：用户确认”，并把 `required_proof=user.signature` 的空槽突出。程序提出的“全能响应”候选需要外部用户的确认与授权来成立，但用户已经离开。于是 God → ROOT、proof → 用户授权形成同一组歌词动作，拒绝与空槽共同表现这个候选无法成立。

上述解释是程序对“全能”的功能化推演，不表示 ROOT 等同于现实中的神。用户位置保持断开，授权始终为空。代码别名 `me` 继续沿用；此时台词不提前使用“我”。本次拒绝是单项权限反馈，不是“连续越权”的汇总警告。

| 47–48，enter / trance | 进入已有嵌套调用图形；不因每次内部调用再刷一条聊天消息 |

说明采用与茄子等候选相同的紧凑节奏：整句提示立即显示，选中字段与修改画面同帧或稍后 80–150 ms 出现，不增加“先读说明、等待、再执行”的独立阶段。F／M、AM／PM、S／M 的实际写入继续贴合其唱词，不为提示或高亮效果额外推迟。后一个动作到点就覆盖前一个短效果，不排队等动画播完。

这一段仍是基于未确认需求的自发参数搜索，不表示用户提出过这些要求。说明和选中字段只是准备动作，不能提前把还未唱到的参数值写入内存。

#### 4.4.1 右侧内存：把属性变化变成可辨认的写入事件

第 41–48 行暂时把视觉重心从主模拟区引向右侧。观众应看到“选中字段 → 写入字节 → 读到新值”，并能把它与 F／M、AM／PM、S／M 对应起来。

| 时机 | 右侧内存与变量区 | 视线引导 |
|---|---|---|
| 进入修改段 | 标题改为亮青色粗体的 `内存 / 属性写入`；自动定位 `gender` 所在地址范围 | 主模拟区对应字段旁短暂显示 `→ MEM`，右侧同色选中条响应；提示与定位最多间隔 150 ms |
| 每次实际写入的最初约 120 ms | 实际变化的字节用亮黄粗体和深色底突出，字段地址与名称一同选中 | 右侧边框短暂提亮；主模拟区的次要代码与边框可降亮约 300 ms，聊天主台词和字幕不降亮 |
| 写入后约 120–450 ms | 一行明确显示旧值→新值，例如 `WRITE gender: F → M`；新值与实际十六进制字节保持对应 | 原值只是写入记录，新值是当前内存；不快速闪回旧值，也不让整窗闪白 |
| 写入后约 450–650 ms | 退回正常亮度，保留当前值；下次写入到来时立即切换焦点 | 不阻塞下一个歌词动作，不为每次变化新增聊天消息 |

焦点顺序与实际字段一致：`gender` → `period` → `role`。每次同时选中字段名、内存地址、实际变化的字节和右下变量值，使用相同的强调色；不能只改变角落里的 revision 数字。示意信息可为：

```text
内存 / 属性写入
> WRITE gender: F → M
  [字段地址] [真实十六进制字节]

变量
  gender = M
  period = AM
  role   = UNSET
```

示意不规定地址和字节常量。地址、旧值、新值、变化范围全部取自实际 store 写入事件；枚举的数值编码不伪装成字母的 ASCII 码。未发生写入时不显示虚假的变化字节或“写入成功”。

为免高亮被挤在很小的角落，这一段右侧内存区可临时占右栏高度约 60%，余下为变量区；至少保留字段写入说明和当前值。130×35 下优先保留焦点字段、实际字节与三项当前属性，压低不相关元数据的显示优先级。右栏不横向扩张，不改变主模拟区边界。

第 47–48 行若转入嵌套调用，右下变量区改为突出真实调用深度与当前栈帧；没有 store 写入就不伪造内存变化。第 49 行探测开始时收回属性写入焦点，恢复常规内存样式。

这些效果均按写入事件的时间、地址和前后值重建，不以渲染帧累积状态。跳转、低帧率或窗口变化不能造成错误的旧值，也不能延长演出节奏。

## 5. Execution：提前开始动作，推迟汇总警告

上表之前已发生的首次 ROOT 申请、会话检查也只显示单项失败。不得因为内部失败次数达到某个阈值，就提前自动插入“检测到连续越权”。

### 5.2 最后一组 Execution 才显示连续越权

第 72 行为最后一组，范围 02:37.860–02:39.080。最后一次失败后，在约 **02:37.980** 首次显示汇总信息：

```text
[guard] 警告！检测到连续的越权尝试。
```

前五组及间奏阶段不能出现这句或同义的“检测到连续提权”。它们只解释当前异常行为为何失败。最后一组才从单项错误升级为连续行为判断。

本版取消旧方案要求汇总警告在计数前单独停留至少两秒的安排：最后一组到计数只有约一秒，后续通过计数中的重复警告和终止定格继续提供阅读时间。guard 不预告“再次提交将被强制终止”，不告知程序处置阈值。

**明确截止：这一整段连续 Execution 的操作尝试、重试动画、单项失败反馈与首次汇总提示，必须在数一（Ein）开始之前完成，不是到数六才结束。** 时间要求为：最迟在 **02:39.080** 收尾，数一于 **02:39.190** 开始，两者不重叠。已写入的聊天记录可以留在画面上，但操作和重试演出不能跨入数一。

### 5.3 先自删，再扩大目标到整个模拟系统

## 6. 六语言计数：聊天警告、上一条的损坏、下一行的新警告

### 6.1 每个数都在聊天框内输出同一条警告

中央大字和六种语言的顺序保留。每个计数开始时先增加背景损坏，约 60 ms 后在聊天记录的下一行写出：

|---|---|---|

这六条是 guard 对已发现连续越权的持续报告，不代表新增六次指令执行。加上第 72 行首次汇总，共七次汇总提示；与各项操作的拒绝日志分别记录。

### 6.2 覆盖必须有先后关系

1. 第一个数开始，原聊天内容随背景一起损坏；新警告在聊天内容区以红色粗体完整出现。
2. 下一个数开始，上一条警告失去前景保护，部分字符被新的异语和乱码覆盖。
3. 随后在聊天下一行输出一条新的完整警告。只有这条最新警告的所在行清底并位于剧情损坏层之上。
4. 后续继续“旧行受损 → 下一行新警告”。不能每帧把全部历史警告重新画成完整红字，抹掉已有损坏。

“下一行”指聊天记录的逻辑下一行。小终端不足以同时显示六行时，聊天按正常视口滚动；保留仍在视口内的损坏痕迹，不把警告固定在同一个物理位置闪烁。最低尺寸下不要求六条同时可见。

警告只能出现在聊天框内容区域。移除当前计数阶段靠近屏幕底部的独立浮层提示，不再以它代替聊天记录。新警告只保护自身一行，不为整个聊天框设置永久防损坏层。

### 6.3 破坏继续累积，不能因为警告暂停

每次数数仍叠加对应语言的局部翻译、跨窗格的无意义内存文本、随机位置的外溢和持续闪烁的乱码。旧损坏不复原，空白区域也逐渐被填满；中央计数保留现有大字与边缘受损效果。

到第六个数，剧情背景基本不再有可读语句；中央计数和刚写出的 guard 警告是短暂可读的前景。**底部观众字幕始终是独立例外**，不参与这个“全屏损坏”。

损坏、聊天滚动和警告位置必须由时间、事件和 seed 重建。跳转到某个数时，应该看到此前各次的累计结果，不能依赖是否实际渲染过前几帧。

## 8. 观众字幕：独立于模拟系统的最后一层

### 8.1 两行、亮白、加粗

中文模式 `--lang cn`：

```text
                     If I can, if I can
                       如果能够，如果能够
```

英文模式 `--lang en` 通常只显示上行原文，下行留空；**六语言计数是例外**：在原本中文译文所在的第二行，显示带圆括号的英文释义。两种模式都预留终端最底部两行，避免切换语言造成剧情布局跳动。

| 计数歌词条目 | 中文模式第二行 | 英文模式第二行 |
|---|---|---|
| 73，Ein / dos | `一，二` | `(one, two)` |
| 74，trois / ne | `三，四` | `(three, four)` |
| 75，Fem / liu | `五，六` | `(five, six)` |

上行仍是对应条目的原唱歌词；英文模式的括号行翻成英文，不显示中文，也不占中央大计数的位置。保持现有两数一组的歌词单元，不为了六次中央计数而把字幕拆成六次闪切。第 76 行 Execution 开始时清空括号行，恢复英文模式通常的单行显示；括号译文同样亮白加粗，不受损坏影响。

- 中文模式上行英文原文，下行中文译文，各自水平居中；中文不代替英文。英文模式遵循上述计数例外。
- 所有可见字幕均为亮白色、粗体，建议 ANSI 色 `15`、`bold=true`、黑色背景。英文计数的括号译文与主行相同，不降低亮度。
- 不附角色标签、歌词编号、时间码、校准偏移或控制提示；这些信息不能挤占观众歌词。
- 不使用失焦、抖动、变色、损坏、淡出或低亮度。两侧至少留两列排版余量，按实际显示宽度计算中文与其他宽字符。
- 以现有歌词条目为单位显示，不提前加入逐字变色或卡拉 OK 效果。

### 8.2 字幕区不属于剧情系统

```text
┌────────────────────────────────────────────┐
│ 剧情区：窗口／损坏／警告／终止／自检／归档 │
│                                            │
├────────────────────────────────────────────┤
│                 英文歌词                   │
│                 中文译文                   │
└────────────────────────────────────────────┘
```

上图仅说明层级，不要求在字幕周围绘制边框。物理终端为 `C×R` 时，剧情视口高度为 `R−2`；最后两行是观众字幕区。

普通窗口、内存外溢、异语翻译、乱码、重影、白框、自检和归档滚屏都必须裁剪在剧情视口内。字幕从音乐时钟读取当前行，在所有剧情绘制完成后单独绘制。

建议绘制顺序：

1. 正常剧情窗格与内容。
2. 累积翻译、内存文本外溢与闪烁乱码。
3. 中央大计数。
4. 聊天区域内最新的一行 guard 警告。
5. 位于聊天框下方的终止白框；或终止后的系统自检／归档控制台。
6. 底部两行黑底与观众字幕。

白框阶段只缓存冻结的剧情区，不缓存整个最终画面。自检阶段不恢复 sim 窗口，也不影响字幕。字幕显示不构成进程继续运行或收到用户反馈。
