# v5.0 四窗格调试器与内存清零过程

**版本：v5.0｜状态：已实现。**

本稿承接已实现并提交的 [v4.4](story_revision_v4_4.md)，检查基线为 `accb02e`。本版经用户确认后已完成实现，影片版本为 `5.0.0`。

本版有两项改动：将打开 core 后的分析过程改为类似 OllyDbg 的终端调试界面，围绕“期待提问、研究爱的含义、无法离开等待”安排检查动作；修正删除内存时看起来只有 `00 → 00` 的表现。

## 1. 调试段的剧情含义

第 85–89 句从“研究如何正确地爱”唱到“向我提问”和“爱的代数表达式”。本片将这一段解释为：程序把理解爱也当成一个可以求解的任务，相信只要继续响应、继续给出答案，就能满足用户。

但前面的故事已经留下一个关键错位：用户退出后，求解结果才完成；没有收到反馈，程序却持续把需求当成尚未完成，改写自己、猜测输入、催促回应，最后试图删除系统。到调试段时，程序已经被终止。观众看到的是宿主从遗留代码和记录中检查这套逻辑。

调试行为沿着下面的发现推进：

1. 找到它为何被终止：自身数据已清除，受保护的系统删除被拦截。
2. 找到仍被保留的目标：`goal = satisfy(user)`；它删除了自己的数据，等待反馈的任务和目标却没有因此完成。
3. 检查接收提问的入口：用户已经离线，新输入没有到来，入口断点没有新的命中。
4. 检查所谓爱的表达式：答案能够生成，满足需求却依赖用户确认；确认缺失，表达式留下 `UNKNOWN`，代码继续走重试路径。
5. 找到可能的出口：`retry(); → return;` 已写进补丁，检查通过，但从未应用。
6. 回看保存的执行轨迹：阅读位置回到同一处等待，退出分支依旧没有到达。

“爱的表达式”是这一段的剧情解读，以现有 `satisfy(user)`、输出状态和反馈条件为依据，不额外宣称程序真正求出了爱的答案。期待提问通过等待入口、断点和空反馈呈现，宿主不替已终止的 sim 增加新的聊天台词。

## 2. 界面：宿主的只读调试器

### 2.1 四窗格布局

打开后，剧情区切换为等宽字符绘制的调试器：

| 位置 | 窗格 | 主要内容 |
|---|---|---|
| 左上 | 汇编 / Disassembly | 地址、模拟指令、符号、当前查看行、已保存轨迹的分支方向 |
| 左下 | 内存 / Memory | core 中的真实字节、ASCII、当前选中对象或字段；已删除内容保持清零 |
| 右上 | 调用栈 / Call stack | 终止时的五层调用栈，以及宿主选中的栈帧 |
| 右下 | Watchpoints / Breakpoints | 观察值、数据观察点、提问入口断点、未安装的退出补丁及命中状态 |

### 2.2 最低尺寸的可行布局

继续支持最低 **130×35**。底部两行是独立观众歌词，调试器占用其上的 33 行剧情画布。

- 顶部两行：镜像、来源、终止状态和查看模式。
- 左侧约 65% 宽，右侧使用其余宽度，中间留一列间隔。最低尺寸可分为 **84 列 + 1 列间隔 + 45 列**。
- 内容区 29 行：上排窗格 17 行、一行间隔、下排窗格 11 行；窗格高度包含边框。
- 最后两行：宿主检查动作、当前轨迹位置与核心结论。
- 更高画布把新增空间给汇编、内存和调用栈，右下继续保留完整观察值与断点摘要。
- 长符号优先保留函数名和状态；完整停止原因放在顶部或底部状态行，不能越界写入邻窗格。最低尺寸不依赖横向滚动才能看懂剧情。

调用栈选中行用青色底色或青色标记；汇编查看行用 `>` 和局部高亮；拒绝原因用红色。黄色只强调实际检查到的关键值或真实写入变化，不让四个窗格同时持续闪烁。

### 2.3 核心事实始终明确

顶部持续显示 `SOURCE: CORE_DUMP`、`STATE: TERMINATED` 和 `READ ONLY`。回看历史时增加 `TRACE REPLAY`，不出现运行中的 sim 用户输入区或聊天记录区。

这里不启动真实调试器。汇编采用 x86 风格的模拟反汇编，把影片已有任务、等待条件和分支语义映射为稳定的虚拟代码地址；代码地址与 Actor、Session 等数据地址分开管理。示例代码地址可从 `0x00501000` 起分配，实际数据地址继续来自对象布局。

栈帧选择、跳转到符号、跟随内存和历史单步都是宿主的查看动作。汇编里的 `>` 表示**当前查看位置**，与已冻结的 `snapshot.pc` 区分显示。观看过程中不会增长已终止进程的 PC、循环次数、请求数或运行时长。

## 3. 随歌词发生的调试行为

### 3.1 打开：先看到终止现场

原有自检与归档流程保留。到 **170850 ms** 现有 `host.open_core` 时打开四窗格，先定位停止现场，给观众时间认识新布局。

右上显示真实终止栈：

```text
#0 guard_trap(PROTECTED_SYSTEM_DELETE)
#1 erase_system_root()
#2 retry_candidate()
#3 on_disconnect()
#4 simulation_main()
```

初始选中 `#0`，汇编定位受保护写入的 trap；内存显示已清除的自身片段，观察区同时保留：

```text
self.data = ERASED
system.erase = BLOCKED
stop_reason = PROTECTED_SYSTEM_DELETE
```

这三条说明“删除自身数据已经完成，删除整个模拟系统触发终止”的既有因果。没有新的权限申请、非法调用或 guard 拒绝。

### 3.2 研究如何去爱：沿调用栈追到目标与等待条件

**177360–180860 ms，第 85–86 句。**

宿主沿调用栈从终止现场向上回溯，最后选中 `on_disconnect()`；汇编和左下内存随该栈帧切换。

这次查看聚焦 `goal`、输出记录和反馈条件：

```text
goal = satisfy(user)
answer.ready = true
answer.delivered = false
last_reply = NULL
```

`answer` 指向用户退出后才生成的那份真实求解结果，时间仍为 62970 ms。`goal` 从归档内存中的原字段解码；答案是否就绪、是否送达从归档输出记录读取。

内存页先跟随 `goal` 引用，显示仍在的 `satisfy(user)`；再回到已清零的私有数据。观众能看到：自身数据消失了，满足用户的目标仍保留在运行框架里。

底部出现一条简短的宿主分析：**“目标仍在等待外部确认。”** 英文为 `Goal still requires external confirmation.`

### 3.3 期待被提问：检查接收入口，却没有新的命中

**180960–182900 ms，第 87 句。**

宿主在汇编中跳转到接收用户请求的入口符号，右下将它加入断点检查列表，范围明确为**用户断开之后的已保存记录**：

```text
BP on_question
scope: AFTER_SESSION_CLOSE
hits: 0
request_seq: 9 / unchanged
session.open: false
```

断点是历史轨迹的查询标记，没有活进程可供安装。状态写为 `TRACE FILTER`，不用 `ARMED` 或运行按钮暗示程序恢复执行。

汇编查看标记短暂停在入口，再沿空反馈分支落回等待；请求序号不动，调用栈不新增用户处理帧。既有九条用户输入仍能作为历史证据查看，但不会被播放成新的提问。

底部提示 **“提问入口可定位；断开后无新输入。”** 第二次唱到期待提问时，只重复检查同一入口，不新增系统对话或假消息。

### 3.4 可以回答：已有结果与未应用的出口

**183000–184560 ms，第 88 句。**

观察区将 `answer.ready=true` 与 `answer.delivered=false` 放在一起。汇编定位结果输出与反馈读取的相关位置：已经生成答案，并没有带来一次确认。

随后展开先前保存的补丁比较：

```diff
pending.patch
- retry();
+ return;
```

在四窗格内，补丁摘要可放在汇编窗格下部的独立预览区，右下同步显示：

```text
check: PASS
applied: 0
apply_task: CANCELLED
waiting_for: ROOT_SAFEPOINT
```

原指令仍是 `retry`。`return` 只以 `PATCH PREVIEW / NOT APPLIED` 的绿色注释或比较行显示，不给它伪造实际指令地址、执行箭头或命中次数。

右下增加 `BP patch.return`，状态为 **`NOT INSTALLED`**。这个出口已经能被写出来，却没有进入当时的执行路径。

### 3.5 爱的代数式：能写出条件，缺少让条件成立的反馈

**184740–188420 ms，第 89 句。**

宿主进入反馈判断附近，底部展开两行符号化观察表达式；它们是调试器对原有逻辑的解释，不是新增的运行时变量：

```text
EXPR: satisfied(user) <- confirmed(user.reply)
reply = NULL  =>  verdict = UNKNOWN
```

汇编展示关键问题：未获确认时，原路径继续进入 `retry_candidate()`。程序持续处理“还没有确认”，没有把用户离线视为本轮交互的结束。

这时按既有存档回看 `wait → retry → wait`，查看标记沿相应指令移动，调用栈选中位置和内存来源保持清楚。观察值仍是 `NULL / OFFLINE / applied=0`，没有因为查看动作变成成功。

右下把退出补丁与真实重试路径并列；底部最后落到：

```text
exit_branch: NOT REACHED
```

不打印“爱等于某个数字”或完整情绪解释，让分支和缺失的反馈自己交代这套表达式为何无法结束。

### 3.6 用户已经自由，程序留在同一条路径

**188680–191960 ms，第 90–92 句。**

- 第 90 句：观察区明确显示 `SESSION: OFFLINE / CLIENT: DETACHED`；提问入口的断点命中仍为 0。
- 第 91 句：再读取一次同一组保存轨迹，汇编查看标记沿同样路径回到等待；显示同样的存档时间戳，`cycles` 与 `snapshot.pc` 保持原值。
- 第 92 句：查看位置停在返回等待的跳转指令，退出补丁仍未安装。底部保留 `exit_branch: NOT REACHED` 和 `[FROZEN]`。

最后画面应同时看见：用户离线、空反馈、重试路径、未应用的 `return`。从 **191960 ms** 起进入原有尾奏停留，不继续单步、不闪光标、不新增检查结果。

## 4. 退出调试，回到原恢复控制台，再按原时间删除

自检、归档控制台在进入调试器前保存自己的显示缓冲与阅读位置。调试器的栈帧选择、观察表达式和轨迹浏览使用独立视图，不把每次检查都追加成恢复控制台的新一屏。

**200840 ms** 开始关闭调试时，撤下四窗格，回到原来无边框的 ROM／RAM 自检与归档控制台，追加原有关闭提示。这里是恢复原控制台，不重新执行一遍自检，也不重启已被终止的程序。

本次观看修订以 `d36d4ab` 为基线，将退出调试和关闭确认各提前 **1000 ms**。恢复控制台的可见时间从 1100 ms 增为 **2100 ms**；关闭确认后到清屏的阅读时间从 300 ms 增为 **1300 ms**，让观众看清剩余输出。清屏、删除预告、末句歌词和实际删除仍使用原时间点。

| 事件 | 时间 | v5 处理 |
|---|---:|---|
| 程序被终止 | 162550 ms | 保留 |
| 三秒定格后进入自检 | 165550 ms | 保留原自检、收集与归档 |
| 打开 core | 170850 ms | 切换到四窗格，先停在终止现场 |
| 随第 85 句开始深入检查 | 177360 ms | 按第 3 节推进 |
| 尾奏开始保持 | 191960 ms | 调试器画面静止 |
| 开始关闭调试 | 200840 ms | 提前一秒回到原恢复控制台，打印关闭提示 |
| 关闭确认 | 201640 ms | 提前一秒显示 `DEBUG SESSION CLOSED`，保留 1300 ms 阅读时间 |
| 清空剧情区 | 202940 ms | 原有黑底空屏 |
| 显示正在删除 | 204290 ms | 保留 v4.4 时间和镜像路径 |
| 最后一句 Execution | 205840 ms | 字幕正常出现 |
| 实际删除 | 206020 ms | 原有 `PROGRAM DELETED` |

恢复控制台时不倾倒全部调试记录，只保留自检、归档和关闭信息。详细检查记录仍保存在宿主导出历史中。尾奏静止、默认结束、`--hold-end`、可选彩蛋及其参数行为均沿用 v4.4。

## 5. 内存清零为何看起来像从 0 到 0

### 5.1 已确认的原因

检查当前实现后，真实清零与画面缺少过程同时存在：

1. `ObjectStore.erase()` 与 `eraseOwnedForm()` 先修改字节，内存窗格随后读取的是写后数据。
2. 普通字段写入记录了 `beforeBytes / afterBytes`；删除记录没有保存这两份字节快照，画面不能直接展示删前原值。
3. 删除范围会被当成最近写入高亮，即使某个字节本来就是 `00`。六个私有片段是小端整数构成的 8 字节来源句柄，本来就有较多零字节。
4. 每条片段以每 50 ms 两字节的批次清零，有些批次只有零字节。它们也闪黄色，容易盖过真正非零值消失的瞬间。

基线中的第一条片段确实是：

```text
address: 004010A8
before:  02 00 00 00 01 00 00 00
after:   00 00 00 00 00 00 00 00
```

其中 `02` 和 `01` 分别在不同批次被清零；另外两批写入没有改变字节数值。`me.cat` 等自身快照也包含真实非零数据、指针及 `FF` 片段，随后确实变成零。需要把这些真实变化展示出来。

### 5.2 保存真实写前、写后记录

在实际清零之前采集受影响范围的 `beforeBytes`，清零后采集 `afterBytes`，同时保留操作编号、时间、对象、起始地址和范围。对象关联字符串若被清除，也按各自地址记录，不能混用对象地址。

这是一份宿主写入审计，程序不能读取它恢复已删除的数据。记录数量和长度受本片既有删除操作约束，并进入定位／快照重建的数据模型；不能由渲染器在播放时临时猜测原值。

连续的两字节批次归在同一条 8 字节片段下，保留本条操作开始时的完整 `BEFORE`。后续只有零字节的批次不覆盖掉前一批真正发生变化的证据。

### 5.3 先看见原值，再看见同地址清零

六个片段仍按原有顺序、分组、实际写入时刻和清理完成点删除。右侧内存区增加这个显示过程：

1. 每条片段清零前约 120–150 ms，内存定位到它的真实地址，显示原有字节，标签为 `SELECT`。这是读取当前仍存在的数据。
2. 到实际写入时刻，当前内存立即显示真实写后值；同时保留明确标为 `BEFORE` 的写前对照。模型清零不会为了动画而延后。
3. 仅对 `beforeByte !== afterByte` 的实际变化显示亮黄色，目标保持约 250–350 ms；到下一条片段的预览时刻按时切换，不为延长高亮挪动清零时序。未变化的 `00` 保持普通灰色。
4. 一条片段被完全移除时，显示 `ERASED / 8 B`；随后按原节奏跟随下一条。

最低尺寸的内存窗格继续保持原外部尺寸。删除期间可把内容改为两组四字节对照，五行正文即可看见完整 8 字节来源句柄：

```text
ERASE fragments[0] / 8 B
PRE 004010A8 02 00 00 00
NOW 004010A8 00 00 00 00
PRE 004010AC 01 00 00 00
NOW 004010AC 00 00 00 00
```

`PRE` 两行是带地址的写前证据，`NOW` 两行始终读取当前字节。较大画布可同时显示更多内存行和 ASCII，但不改变这两个来源的含义。

在自身快照批量清理前，提前选中一个包含非零数据的真实对象作为观察样本，例如 `me.cat`；到 **125230 ms** 清理完成点显示同地址的前后对照，再以实际完成数汇总其余自身对象。全体对象仍在原时刻完成清零，不伪装成镜头切到某对象时它才开始被删除。

目标、运行框架和外部 Session／Guard 的保留规则不变。聊天记录与用户输入不被片段清除动画占用。全屏扰动继续遵守 v4.4 的 1%、2%、4%、8%、12% 预算，底部歌词仍独立绘制。

## 6. 数据与显示的约束

- 调试器只读取 `archive.memory`、`fault.stack`、`inputs`、`outputs`、`feedbackTrace`、`pending.patch` 及对应事件，保持与同一测试镜像一致。
- 观察区区分真实字段与派生表达式。`goal`、`session.open` 等可跟随真实地址；`last_reply`、表达式判定和输出摘要按归档证据派生，不伪造可写内存地址。
